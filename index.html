Philosophy

What I Care About

Three core operational principles that guide how I design, write, and debug software in production.

01

Design for retries and partial failure by default

Production bugs are usually coordination bugs. Flaky mobile links, external gateway drops, and server timeouts are normal. I build with idempotent transactions, outbox queues, and circuit breakers rather than assuming happy-path success.

02

AI systems need validation boundaries

LLMs are probabilistic. To build stable systems with them, we must treat structured outputs, validation guards, and retrieval metrics as core backend infrastructure. Never trust raw model outputs without validation.

03

Local-first sync is a user experience feature

Syncing local offline databases and optimistic frontend states is a distributed systems problem in disguise. But the goal is purely human: let users write instantly without watching spinners, regardless of network conditions.

Mobile & Sync Systems

Ember: Real-Time Sync & Habit Platform

A mobile social habit tracking application featuring a local-first sync engine, optimistic state reconciliation, and real-time group leaderboard aggregation.

Stack React Native, AWS Lambda, AppSync GraphQL, DynamoDB
Core Patterns MMKV Offline Outbox, SQS FIFO, DynamoDB Streams

The Challenge

Mobile networks are highly unreliable. Coordinating active habit logging, group check-ins, and animated heatmaps without freezing the UI or allowing duplicate entries during reconnects required offloading the write path and managing conflicts locally.

Key Decisions

  • MMKV over AsyncStorage: React Native's default storage created a noticeable UI stutter when serializing daily progress records during optimistic renders. MMKV reduced serialization latency, keeping renders locked at 60fps.
  • SQS FIFO Queues: Group leaderboard aggregates required deterministic event ordering during reconnection sync waves. FIFO routing prevented out-of-order execution and simplified group score reconciliations.

What Broke & How I Fixed It

Under poor network links, AppSync subscription sockets would drop silently. Users who updated habits offline returned to a screen that drifted from the server state. I resolved this by designing an offline transaction outbox. When offline, updates are persisted locally with unique idempotency keys. On reconnect, a background worker drains the outbox to a retry endpoint, utilizing high-water marks to avoid overwriting newer server modifications.

Campus Connect: Digital Marketplace

A serverless marketplace for physical and digital campus goods, secured with stateless authorization and gating download entitlements.

Stack React (Zustand), AWS Lambda, DynamoDB, API Gateway, S3
Core Patterns Stripe Webhooks, Custom Lambda Authorizers, Gated Presigned URLs

The Problem

Digital asset stores face a common issue: users sharing asset links directly, bypassing checkout. Delivering purchased digital assets instantly while guaranteeing link security required a dynamic entitlement-gating layer that scales seamlessly.

Architecture

Built using a serverless backend composed of specialized Lambda workers. All user endpoints are gated by a Custom API Gateway Authorizer that checks JWT validation signatures and securely caches authorization policies in memory to minimize verification latency.

Reliability Considerations

To secure digital purchases, raw asset files are kept in private S3 buckets. Upon a validated purchase (routed via Stripe webhooks), the backend generates a short-lived (120s) presigned S3 URL dynamically. During k6 load testing with 2,500 concurrent users, hot-partition bottlenecks appeared on category queries. I resolved this by appending a synthetic hash suffix to the category primary keys, distributing read/write throughput evenly across database partitions.

AI Document Processing Pipeline

Stack Python, FastAPI, Vector Indexes, BM25 Search, Redis
Core Patterns Structured Tool-Calling, Pydantic Schema Guards, Semantic Cache Bypasses

System Overview

Built for complex operational environments, this system converts raw text documents into validated structural datasets. It uses multi-step agent verification loops that coordinate vector indices and structured tool calls to extract critical details without manual overhead.

Core Challenge

Since LLMs are probabilistic, raw generations can easily hallucinate structural details or drift from facts. We needed to keep the extracted outputs strictly grounded, reduce latency spikes from model evaluations, and make system failures completely observable in production.

Implementation

I designed a dual-stage retrieval engine combining semantic vector search with lexical BM25 rerankers to surface highly relevant grounding paragraphs. Raw outputs are parsed against strict Pydantic schema validation boundaries at the API gateway layer. To optimize throughput, I implemented a local semantic caching layer (Redis) that maps vector embeddings of incoming requests: queries matching existing cached intents with high cosine similarity bypass LLM calls entirely, reducing P50 latency.

Distributed Payments

Preventing Duplicate Payment Execution in Distributed Systems
Problem

During downstream payment gateway instability, cross-border network retries on SocialPay microservices periodically triggered double transactions inside third-party ledger integrations, risking financial state drift.

Why It Was Difficult

External payment routes returned non-deterministic connection timeouts. Under stress, mobile users naturally tapped the confirmation button multiple times, generating parallel client requests that bypassed simple transient locks.

Failed Approaches
  • Database row locking: Created heavy transactional contention on the core tables, degrading general API performance and leading to connection pooling exhaustion under load.
  • Naive retry suppression: Dropped legitimate network confirmations during valid partial gateway recoveries, locking users out of completed orders.
Final Design

I structured a transaction-scoped idempotency filter powered by Redis. Every payment request maps a unique idempotency key derived from the checkout session ID and product scope. Incoming duplicate calls lock on this key, waiting to retrieve the initial payment intent status. Combined with Spring State Machine transitions and Resilience4j circuit breakers, we isolated downstream gateway time-outs and eliminated duplicate transactions completely, achieving 99.95% payment platform uptime.

Mobile Offline-First

Designing Local-First Sync Under Unreliable Networks
Problem

Mobile users tracking goals in Ember experienced frequent, silent sync disconnects under variable cellular networks. The local client state diverged from backend database partitions, creating confusing UI rollbacks on app restarts.

Why It Was Difficult

Syncing offline writes requires merging conflicts in a specific sequence without duplicating entries. If a user logs three accomplishments offline, the client must serialize and queue events, applying merge reconciliations on reconnect without locking the UI thread.

Failed Approaches
  • React Native AsyncStorage: Serializing state updates on the main thread blocked JS event execution, dropping frames from 60fps down to 24fps during background sync sweeps.
  • Last-Write-Wins (LWW): Standard date-based syncing led to silent data overwrites when offline devices with drifted local clocks reconnected.
Final Design

We switched to an MMKV-backed transaction outbox. When offline, progress actions write instantly to MMKV and update the optimistic Zustand cache, maintaining a 60fps render loop. Every write registers a monotonic sequence ID and unique transaction key. Upon reconnecting, a background task synchronizes the queued outbox events sequentially using high-water mark validation filters. Errant sync rejects are isolated in a local Dead-Letter vault, alerting the user via a minimal home-screen recovery banner to manually retry or clear failed states.

Database Performance

DynamoDB Hot Partition Debugging via k6 Load Testing
Problem

During stress testing with 2,500 concurrent virtual users querying Campus Connect listings, P99 API response latency spiked from 120ms to over 12 seconds, eventually dropping requests with HTTP 502 Bad Gateway timeouts.

Why It Was Difficult

AWS API Gateway logs initially pointed to Lambda cold starts. However, tracing with AWS X-Ray revealed that the bottleneck occurred on database read operations. The primary query path queried listings by a concentrated logical GSI index (e.g. `Category = Textbooks`), causing AWS to throttle queries on a single physical database partition.

Failed Approaches
  • Provisioning manual capacity: Increasing read capacity units (RCUs) did not resolve the bottleneck, since the queries still hit the same physical partition block, wasting budget on unutilized overhead.
  • Global caching: Using standard caches masked the problem but introduced state synchronization delays when students added or deleted active listings.
Final Design

I implemented synthetic partition sharding on the DynamoDB global secondary index. By appending a deterministic hash suffix (`Category#HASH`, derived from `ProductID % 4`) to the partition key, we distributed the logical GSI records evenly across four physical AWS storage partitions. The client endpoint queries all four shards in parallel and merges the arrays. This eliminated partition throttling entirely, dropping P99 latencies back to a stable 85ms under full 2,500 concurrent load.
